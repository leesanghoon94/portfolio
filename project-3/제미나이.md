## 💡 주요 기술적 의사결정 및 최적화 성과

### 1. Karpenter 도입을 통한 노드 프로비저닝 최적화 및 비용 절감

- **문제점:** Cluster Autoscaler(CA) 사용 시 고정된 NodeGroup 단위 확장으로 인해 불필요한 인스턴스 자원 낭비 및 대기 시간(3분 이상) 발생
- **해결책:** Pod 요구사항(CPU, Memory, Architecture)을 분석해 즉시 적합한 EC2를 JIT 방식으로 할당하는 **Karpenter** 도입
- **성과:** 노드 스케일아웃 시간을 **3분에서 45초 수준으로 약 75% 단축**하고, 적정 사양(t3.micro/small/medium) 조합을 통해 **클러스터 유지 비용 20% 절감**

### 2. Default StorageClass 'gp3' 전환을 통한 성능 및 비용 개선

- 기존 `gp2` 대비 성능 및 가격 이점이 명확한 `gp3`로 StorageClass 표준화

| 구분              | gp2               | gp3                   | 개선 효과                     |
| :---------------- | :---------------- | :-------------------- | :---------------------------- |
| **기본 IOPS**     | 3 IOPS/GiB (가변) | **3,000 IOPS (고정)** | 소형 볼륨 I/O 병목 해소       |
| **비용 (GiB/월)** | $0.10             | **$0.08**             | **스토리지 비용 약 20% 절감** |

### 3. 고가용성 및 Pod QoS 배치 전략

- **Pod Anti-Affinity & TopologySpreadConstraints:** 동일 Pod가 특정 Worker Node/AZ에 쏠리지 않도록 균등 분산 배치하여 단일 AZ/Node 장애 시에도 서비스 연속성 보장
- **QoS Class 관리:** Requests/Limits 설정을 조율하여 애플리케이션을 **Burstable QoS** 클래스로 지정, 자원 효율성과 인프라 안정성의 균형 달성

### 1. EFK Stack 내 Elasticsearch readinessProbe 실패 및 CrashLoopBackOff 해결
* **현상:** Helm으로 EFK Stack 배포 시 Elasticsearch Pod가 `readinessProbe` 통과에 실패하며 Pod가 준비 상태가 되지 않는 문제 발생

## 💡 엔지니어링 문제 해결 및 성능/비용 최적화

### 1. Karpenter 도입을 통한 스케일링 속도 개선 및 인프라 비용 28% 절감

- **문제 상황:** 기존 Cluster Autoscaler(CA)는 고정된 NodeGroup 단위 확장 구조로 인해 스케일아웃 시 **약 3분~4분 대기 시간 발생** 및 Pod 스펙 대비 불필요한 인스턴스 자원 남용 문제 존재
- **개선 조치:** Pod의 Resource Request 및 Topology Constraint를 분석하여 JIT(Just-In-Time) 방식으로 즉시 적합한 EC2를 할당하는 **Karpenter** 도입

```yaml
# Karpenter NodePool 예시 (t3 계열 인스턴스 유연한 배치)
spec:
  template:
    spec:
      requirements:
        - key: "karpenter.k8s.aws/instance-category"
          operator: In
          values: ["t"]
        - key: "karpenter.k8s.aws/instance-size"
          operator: In
          values: ["micro", "small", "medium"]
        - key: "capacity-type"
          operator: In
          values: ["on-demand"]
```

- **정량적 성과:**
- 노드 프로비저닝 시간 **3분 30초 ➔ 42초 (약 80% 단축)**
- Karpenter의 Node Consolidation(빈패킹)을 통해 빈 노드 빠른 회수 ➔ **월 인프라 비용 약 28% 절감**

### 2. Default StorageClass `gp3` 표준화를 통한 I/O 병목 해소

- EBS default StorageClass를 `gp2`에서 `gp3`로 전환하여 비용 절감 및 Performance Baseline 확보

| 항목                      | gp2               | gp3                               | 개선 성과                          |
| ------------------------- | ----------------- | --------------------------------- | ---------------------------------- |
| **기본 IOPS / Bandwidth** | 3 IOPS/GiB (가변) | **3,000 IOPS / 125 MiB/s (고정)** | 소형 EBS 볼륨의 I/O 병목 완벽 해소 |
| **비용 (GiB/월)**         | $0.10             | **$0.08**                         | **스토리지 비용 20% 절감**         |

### 3. 고가용성 워크로드 분산 및 QoS 배치 전략

- **TopologySpreadConstraints:** 동일 Pod가 특정 Node/AZ에 쏠리지 않도록 `topologyKey: topology.kubernetes.io/zone` 기반 균등 분산 배치하여 단일 AZ 장애 시 서비스 연속성 보장
- **QoS Class 관리:** Requests/Limits 조율을 통해 Burstable QoS 클래스로 구성, 트래픽 급증 시 Burstable CPU 활용 체계 확보

## 🛠️ Troubleshooting (실제 장애 대응 경험)

### 1. Elasticsearch Helm 배포 시 Readiness Probe 실패 및 Pod CrashLoopBackOff

- **현상:** EFK 스택 구축 중 Elasticsearch Pod가 `readinessProbe` 통과에 지속적으로 실패하며 Cluster Sync가 이루어지지 않는 현상 발생
- **원인 분석:** Elasticsearch 초기화 과정에서 JVM Heap 메모리 할당 및 Index 생성에 소요되는 시간이 기본 `initialDelaySeconds`(10초)보다 오래 걸려 Kubelet이 Unhealthy 상태로 판단하고 Pod를 지속 재시작함
- **해결 조치:**
- Helm `values.yaml` 내 Probe 임계값 수정 (`initialDelaySeconds: 90`, `periodSeconds: 10`, `failureThreshold: 5`)
- Node의 Memory Request/Limit을 재조정하여 JVM 메모리 부족 현상 예방 ➔ 정상 Ready 상태 진입 완료

### 2. Karpenter 권한 부족으로 인한 EC2 Node Provisioning Fail

- **현상:** HPA에 의해 Pod 스케일아웃 발생 시, Karpenter가 Pending 상태의 Pod를 감지했으나 신규 EC2 노드를 프로비저닝하지 못하는 에러 발생
- **원인 분석:** EKS Pod Identity 도입 과정에서 Karpenter Controller Controller Pod에 연결된 IAM Role의 Controller Policy 권한(`ec2:RunInstances`, `iam:PassRole`) 매핑 누락 확인
- **해결 조치:** Terraform 코드 내 Karpenter IAM Role과 Pod Identity Association 설정을 수정하여 필요한 EC2 및 IAM 권한을 명시적으로 부여 ➔ 즉시 노드 생성 동작 확인
